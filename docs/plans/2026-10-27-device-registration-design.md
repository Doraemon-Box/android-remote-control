# 重复设备注册修复

## 原因

MainActivity 每次创建一个 SignalingClient，但销毁时没有断开连接；ConnectionService 实际只负责前台通知和唤醒锁，并不接管客户端。旧 Activity 及其回调可能继续重连，形成多个连接。客户端注册时不传 deviceId，服务器每次随机分配新 ID，且没有服务端心跳回收半开连接。

## 实现

- 安装实例持久保存随机 UUID，重新连接和进程重启使用相同注册 ID，不使用型号作为唯一标识。
- 主页面创建时释放旧 holder 中的连接和 WebRTC，销毁时关闭自身连接和重连任务。仅切到后台不会主动断开；系统销毁主页面后需重新打开 App 才会建立新连接。将连接和会话完全迁入 Service 属于后续架构改造。
- 服务端同 ID 新连接替换旧连接、清理旧房间；旧 socket 的延迟 close/error 只清理它自己拥有的注册，不能删除新连接。
- 同一 socket 重复注册保持 ID 不变，兼容不传 ID 的旧客户端。
- 15 秒协议 ping/pong 心跳，下一轮未收到响应则清除连接（失联清理约需 15～30 秒，受事件循环影响）。
- 拒绝被替换或未注册连接发送业务消息；房间转发和关闭均检查成员身份。

## 验证和更新

- Node 16 兼容的 `cd server && npm test` 回归覆盖：连接替换、旧 close 竞态、同型号不同设备、远控房间发送到新连接、旧协议重复注册幂等。
- Android assembleDebug、18 项单元测试、lintDebug 通过。
- 需要同时更新 APK 和 server/server.js，再重启信令服务器。旧 APK 没有稳定身份，不能靠型号安全地去重多个独立旧连接。
- 未直接修改或重启用户的远端服务器。
